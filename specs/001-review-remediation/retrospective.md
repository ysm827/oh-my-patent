## 3. 最有价值的 8 条经验

1. **"成功"信号不等于成功。** PlantUML 在无法解码路径段时返回的是**自己的占位图**（HTTP 200、
   `Content-Type: image/svg+xml`、尺寸正常），不是错误。REQ-042 按字面做完状态码与内容类型校验后，
   REQ-052 依然会被判为"已修复"。→ 凡"外部服务产出即最终产物"的链路，至少要有一条**把产物内容对回输入**的判据。

2. **断言"形状"的测试会给出虚假安全感。** REQ-004 的两条断言（URL 字符集合法、PNG 与 SVG 用同一编码）
   在位序写反时**同样成立** —— 路径段语法合法、长度也对。→ 编码 / 序列化类实现需要一条
   **与外部真实参照物对齐**的向量（本次是一条对 `www.plantuml.com` 实测通过的路径段常量）。

3. **依赖的 `engines` 会静默改写本包的真实下限。** 文档沿用的"Node 18+"来自约定而非测量；
   `ink@^7`（`tui` 域）自身要求 `>=22`，于是 `engines: ">=18"` 等于"安装期静默通过、运行期才炸"。
   → 声明运行时下限前，先扫 `dependencies` 全链的 `engines`。

4. **审计结论会过期，整体性判断最危险。** 旧结论"`npm audit` 7 项漏洞全在 devDependencies"是**假的**：
   `ink → ws` 一条边就足以让 `ws` 落进运行时树。→ `npm audit --omit=dev` 是唯一可信口径，且**修完要重新实测**再写文档。

5. **把某个字段的"值"写成验收标准，会与"该字段随修订演进"冲突。**
   REQ-048 曾把 `Last Amended: 2026-09-15` 当判据，8 个循环后任何新修订都会让它字面失效。
   → 判据写**结构**（尾行含哪些字段、版本是否单调递增、是否留有含三要素的修订记录），不写某一时刻的取值。

6. **"标注在目录"与"标注在每个文件"是两种不同的交付。** REQ-033 把"历史快照"声明放在
   `docs/specs/README.md`，读者从 `PRD.md` 直接进入时看到的第一行仍是「✅ 已实现」。→ 若目标是"避免读者误读"，
   声明必须落在**读者实际打开的那个文件**里。

7. **测试替身必须与校验强度同步演进。** REQ-042 加上响应体校验后，`diagram-pipeline.test.ts` 里的
   `Buffer.from('png-data')` 立刻由"能过"变成"必挂"。→ 加校验的同一批改动里，要扫一遍**所有**替身（本次抓到 2 处）。

8. **环境的固有成本要先量再写超时预算。** 本机删除文件均匀 **46.9 ms/个**（300 文件递归删除 14.06 s，
   与删除守卫无关，`os.tmpdir()` 下同样）。把"清理卫生"放进测试钩子、又按常规机器直觉设预算，
   必然被误判成代码缺陷 —— PDCA-1 记录的两个失败用例就是这么来的，直到 PDCA-7 量出成本才定位。

> **被推翻的结论（同样有价值）**：PDCA-0/1 曾记录"仓库树内递归删除比 `os.tmpdir()` 慢 650×，建议改临时目录"。
> 真因是本机通过 `NODE_OPTIONS` 注入的批量删除守卫（临时目录被豁免）。清空注入后两处**基本相同**，
> 该归因已在 spec 1.0.4 作废并改写。→ 性能归因必须**换掉变量重测**一次再下结论。

  内容一字未改 —— 它是历史记录，不是待修文档。
- **不为修缺陷而做重构**（C-2）。除缺陷本身要求，未动分层与命名。
- **未引入新运行时依赖**（C-5）。运行时依赖仍只有 `ink` + `react`。
- **未动 agent / command / skill 的 id 与数量**（C-3）：14 agents / 9 commands / 6 skills 保持不变。
- **未启用 OIDC / provenance**：需要先在 npmjs.com 侧配置 trusted publisher（**仓库外动作**），
  在此之前加 `id-token: write` + `--provenance` 会直接让发布失败。已在 workflow 注释与 `CONTRIBUTING.md` 中标注待办。
- **未加分支保护 / CODEOWNERS / Dependabot**：不在 52 条 REQ 范围内，属新需求。
- **未做覆盖率门禁**：仓库无覆盖率工具链，"≥ 80% 核心"仍是**review target 而非 gate**，文档已如实标注。

  但本仓库不 vendor Spec Kit 模板，规格流程是人工执行的。

## 5. 遗留与交接

### 5.1 收尾必办（按顺序，且需人工批准）

**当前事实（复核于收尾前，附可复现证据）**

1. **公开面：根提交 `86d0eb3` 的公司地址已在 GitHub 公开暴露。**
   它的 author 与 committer 都是全局（内网）身份，而非 GitHub noreply。核对方式（本文件刻意不抄写该地址）：
   - `git log --format='%an <%ae>' 86d0eb3`
   - `https://github.com/illusionaireal/oh-my-patent/commit/86d0eb3` —— 页面 live，作者 `zengbods`
   - `https://api.github.com/repos/illusionaireal/oh-my-patent/commits/86d0eb3` —— **无需鉴权**即可读到
     `commit.author.email` / `commit.committer.email`
   全仓身份盘点：31 个提交中**只有这 1 个**不是 GitHub noreply（已公开 14 = 13 个 noreply + 该提交；未公开 17 = 全部 noreply）。
   ⇒ 用户诉求「全部使用 GitHub 匿名账号」的实际工作量 = 修掉 1 个提交，但代价是全史重算（见第 4 条）。

2. **推送阻断独立存在，且与匿名化无关。** 2026-09-16 中断的 `git gc` 删除了 6 个未打包松散对象：
   `84c9b131`(spec.md draft) / `c15003e3`(spec.md confirmed) / `cbfe89fa`(CONTRIBUTING.md@`08280ad`) /
   `7fcdc6c6`(root@`1b456eb`) / `86381b4b`(root@`176d422`) / `c8e4fb0d`(plugins/codex@`1eac610`)。
   受影响提交：`08280ad / 176d422 / 9a40fe4 / 1b456eb / 1eac610`。
   **已穷尽搜索，确认不可恢复**：8 个本地 oh-my-patent 副本 + 2 个 zip（`oh-my-patent-v2.zip` / `oh-my-patent.zip`，
   内含松散对象 125 / 2196 个）+ 全盘按对象文件名搜索 → **全部 0/6**。
   现状判据（可直接复现）：
   ```
   git rev-list --objects --all --missing=print | grep -c '^?'   → 6
   git pack-objects --all --stdout > /dev/null                   → fatal: bad tree object c8e4fb0d…
   ```
   ⇒ **在当前历史形状下，推送必然失败**（不是"内容不完整"，是根本无法打包）。
   旧结论「重写未推送区间后即可普通 fast-forward 推送」**已作废**。

3. **唯一可行路径：commit-only rewrite（只重写提交对象）。**
   `git filter-repo` / `rebase` / `cherry-pick` **都必须读取 tree/blob** 才能重算，遇到缺失对象必定失败。
   而提交哈希 = tree + parent + author + committer + message；**只改 author/committer 与 parent 行、原样保留 tree 行**，
   则所有 tree 哈希逐字节不变，全程不打开任何 tree/blob —— 残缺仓库也能跑。
   预演结果（隔离副本；脚本 `rewrite_commits.py <repo> [丢弃列表] [--update-refs]`）：
   ```
   不丢弃：scanned=32 rewritten=32 dropped=0，tree 违规 0        （技法可用，但缺失对象仍被引用 → PACK FAIL）
   丢弃 5：scanned=32 rewritten=27 dropped=5，tree 违规 0
           → 可达缺失对象 0 → git pack-objects --all → PACK OK → 身份只剩 noreply
   内容不变性抽样 5 对（root / 公开 tip / 2aacbaf / 021691e / HEAD）tree 全部 IDENTICAL
   新 root b61bce3 与早先 git filter-repo 公开段干跑结果一致      （两种独立实现互证）
   ```

4. **必须丢弃上述 5 个提交**（其快照已不可重建）。丢弃语义：子提交重挂到最近存活祖先；
   **存活提交的 tree 不变 ⇒ 内容零损失**，只丢步骤粒度（`master` 31 → 26）。
   代价：PDCA-0（`1b456eb`）与 PDCA-1（`1eac610`）不再拥有独立提交，须在 `tasks.md` §5 如实登记。

5. **回填哈希：重写会重算全部哈希（含已公开的 14 个）**，`spec.md` / `tasks.md` / 本文件中引用的**每一个**哈希都作废。
   预演映射（真实仓库同输入 ⇒ 确定性同结果；若重写前再产生新提交则须重跑）：
   ```
   master tip                  ef3f849 → 5c4a92c      公开 tip (0.3.0)  9142e14 → 560e44db
   root                        86d0eb3 → b61bce3      tag 0.2.1         6c711e2 → 17cd2eac
   origin/chore/release-0.3.0  f7be9b3 → 47fed9a0
   ```

6. **推送是破坏性远端操作，须单独明确批准**，且**不能承诺"彻底删除"**：
   改写后 `86d0eb3` 不再被任何分支可达（网页与 API 会 404），但 GitHub 侧对象可能仍保留，
   且 **PR #1/#2/#3 的 `refs/pull/*` 与 `chore/release-0.3.0` 分支可能仍指向旧提交**。
   彻底清除只有两条路：请 GitHub Support 协助 purge，或删库重建（代价：PR / issue / star 全失）。
   已克隆 / 已 fork 的副本无法收回。

7. **与匿名化无关、需单独决定的文档瑕疵**：`README-design-spec.md:118`、`docs/README-en.md:179`、
   `docs/README.md:189`、`docs/specs/PRD.md:10`、`docs/specs/README.md:243` 把维护者写成 `@zengbods`，
   而本仓 GitHub 账号是 `illusionaireal` ⇒ 该句柄指向不存在或他人的账号。
